# Study 專案憲章

## 專案概述

**Study** 是一個前端靜態網站專案，可直接部署至 GitHub Pages，無需任何後端基礎設施。本憲章定義了專案的核心原則、技術標準及治理流程。

---

## 核心原則

### I. 以靜態前端為本

專案專注於可部署至 GitHub Pages 的前端靜態網站。所有功能必須不依賴後端伺服器，使用 HTML、CSS、JavaScript 實現。不得添加服務端邏輯或專有部署要求。

**理由**：確保最小化部署複雜性、最大化可用性及降低維護成本。

### II. 可訪問性優先

網站必須遵循 WCAG 2.1 AA 標準，確保所有使用者（包含身心障礙人士）都能順利使用。語意化 HTML、適當的 ARIA 標籤、鍵盤導航支援為必備項目。

**理由**：網站應包容所有人，提升可用性及法律合規性。

### III. 響應式設計

設計必須在桌面、平板及手機上提供最佳體驗。使用流動式佈局、彈性網格及媒體查詢，確保在所有螢幕尺寸上正常運作。

**理由**：確保跨裝置一致的使用者體驗。

### IV. 效能為要

每個頁面首次加載時間（LCP）MUST 低於 3 秒。優化策略包括：圖片最佳化、程式碼分割、最小化 CSS/JS、靜態資源快取。

**理由**：快速頁面加載提升使用者滿意度及搜尋引擎排名。

### V. 簡潔與可維護性

遵循 KISS 原則（Keep It Simple, Stupid），避免不必要的複雜性。代碼應易於理解、模組化、文件完整，使新貢獻者能快速上手。

**理由**：降低維護成本，提高協作效率。

## 技術堆棧

| 層級 | 技術選擇 | 說明 |
|------|--------|------|
| **標記** | HTML5 | 語意化標籤，遵循 HTML Living Standard |
| **樣式** | CSS3 | Grid、Flexbox，支援暗色模式 |
| **互動** | Vanilla JS 或 Lit | 輕量級框架，無重型依賴 |
| **靜態生成** | 可選工具 | 如需要則用 11ty、Hugo 或類似工具 |
| **部署** | GitHub Pages | 無需額外基礎設施 |

## 開發工作流

### 分支策略

- **主分支** (`main`)：生產就緒代碼，自動部署至 GitHub Pages
- **特性分支** (`feature/description`)：新功能開發
- **修復分支** (`fix/description`)：錯誤修復

### 提交要求

1. 從 `main` 分支建立特性或修復分支
2. 通過 Pull Request 提交變更
3. 至少一名核心維護者審核批准
4. 自動測試全部通過
5. 合併後自動部署

### 代碼審查檢查清單

- [ ] 符合可訪問性標準（WCAG 2.1 AA）
- [ ] 響應式設計檢查（手機、平板、桌面）
- [ ] 效能基準檢查（Lighthouse > 80）
- [ ] 跨瀏覽器相容性驗證
- [ ] 文件及註釋完整

## 質量把關

### 自動化測試

| 測試類型 | 工具 | 通過條件 |
|---------|------|--------|
| **可訪問性** | Axe DevTools | 0 違規 |
| **效能** | Lighthouse | LCP < 3s, CLS < 0.1 |
| **跨瀏覽器** | 可選自動化 | Chrome, Firefox, Safari, Edge 最新版 |
| **行動測試** | 視覺回歸 | 手機視口下無破損 |

### 效能基準

- **Largest Contentful Paint (LCP)** < 3 秒
- **Cumulative Layout Shift (CLS)** < 0.1
- **First Input Delay (FID)** < 100ms
- **頁面大小** < 500KB（首次加載，壓縮後）

## 治理

### 憲章修改流程

1. 在 Pull Request 中提案修改
2. 說明修改理由及影響
3. 經核心維護者批准
4. 更新版本號

### 版本管理

遵循語義版本控制（Semantic Versioning）：

- **主版本** (X.0.0)：核心原則變更或移除（向後不相容）
- **次版本** (X.Y.0)：新增原則或重大功能擴展
- **修訂版本** (X.Y.Z)：釐清、文字調整、非語義性改進

### 合規審查

每季度進行一次合規審查，確保：
- 所有新增功能符合本憲章
- 效能基準持續達成
- 可訪問性標準未降低

### 衝突解決

優先順序：**可訪問性** > **效能** > **功能** > **新穎性**

若技術方案在上述維度有衝突，優先保證前者。
