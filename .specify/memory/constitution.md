## 核心原則

### I. 以靜態前端為本
專案專注於可部署至 GitHub Pages 的前端靜態網站。所有功能必須不依賴後端伺服器，使用 HTML、CSS、JavaScript 實現。不得添加服務端邏輯或專有部署要求。

### II. 可訪問性優先
網站必須遵循 WCAG 2.1 AA 標準，確保所有使用者（包含身心障礙人士）都能順利使用。語意化 HTML、適當的 ARIA 標籤、鍵盤導航支援為必備項目。

### III. 響應式設計
設計必須在桌面、平板及手機上提供最佳體驗。使用流動式佈局、彈性網格及媒體查詢，確保在所有螢幕尺寸上正常運作。

### IV. 效能為要
每個頁面首次加載時間 MUST 低於 3 秒（LCP）。優化策略包括：圖片最佳化、程式碼分割、最小化 CSS/JS、靜態資源快取。

### V. 簡潔與可維護性
遵循 KISS 原則（Keep It Simple, Stupid），避免不必要的複雜性。代碼應易於理解、模組化、文件完整，使新貢獻者能快速上手。

## 技術堆棧

- **標記**：HTML5（語意化標籤）
- **樣式**：CSS3（支持 Grid 和 Flexbox）
- **互動**：Vanilla JavaScript 或 Lit（輕量級框架）
- **構建**：靜態生成器或簡單構建工具（無需伺服端）
- **部署**：GitHub Pages（無其他依賴）

## 開發工作流

1. **功能開發**：從 `main` 分支建立特性分支 (`feature/...`)
2. **代碼審查**：所有變更必須通過 Pull Request，至少一人審核
3. **測試要求**：視覺回歸測試、可訪問性檢查、效能基準測試
4. **部署**：合併至 `main` 分支後自動部署至 GitHub Pages

## 質量把關

- **可訪問性檢測**：自動執行 Axe、Lighthouse 檢查
- **效能監測**：Core Web Vitals 監測（LCP、CLS、FID）
- **跨瀏覽器相容性**：測試 Chrome、Firefox、Safari、Edge 最新兩版本
- **行動優先測試**：確保行動設備上的完整功能

## 治理

**修改流程**：憲章修改需在 Pull Request 中明確說明理由，經核心維護者批准後方可實施。

**版本管理**：遵循語義版本控制：
- **主版本**：核心原則變更或移除
- **次版本**：新增原則或重大功能擴展
- **修訂版本**：釐清、文字調整、非語義性改進

**合規審查**：每季度審查一次，確保所有新增功能符合本憲章。
